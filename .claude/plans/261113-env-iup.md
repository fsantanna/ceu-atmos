# env-iup: graphical user interfaces for Atmos, over IUP

Plan for the repository `ia-atmos/env-iup`, session `iup`.
Written in the session that maintains the compiler (`ia-atmos/lang`).

## Context

- An environment connects an Atmos program to the outside world: it
  runs the loop of a library, turns its input into events, and offers
  its operations as functions. In this implementation it is a file in
  Atmos with C in native literals, brought in with `include`.
- This one is for graphical user interfaces, over IUP (Tecgraf,
  PUC-Rio): a small toolkit in C with native controls.
- The interest for the language: an interface is made of callbacks,
  and the logic of a dialog is a sequence in time (open, wait for an
  action, validate, close). The games of the other ports show the
  model on animation and physics; this shows it on forms.
- The compiler is `ia-atmos/lang`, branch `main`. Read `doc/manual.md`
  there before writing code: "Environments", "Native Literals",
  "Native", "Include", "Pin".

## Settled decisions

The author decided these. The items marked "(confirm)" are
recommendations that he has not answered: ask, one at a time, before
building on them.

- **Repository**: `ia-atmos/env-iup`, commits straight to `main`, in
  small grains, pushed as you go. No other branch, no pull request.
- **A direct binding to the C interface of IUP**, in one file at the
  root (`iup.atm`), with its functions in one table `iup`.
- **Thin and generic** (confirm): a control is created by the name of
  its class, its attributes are set and read as strings, and its
  callbacks become events. Not one function per control: IUP has
  about a hundred, and its own interface is already generic
  (`IupCreate`, `IupSetStrAttribute`, `IupGetAttribute`,
  `IupSetCallback`).
- **What to build over it** (confirm): the seven tasks of 7GUIs
  (counter, temperature converter, flight booker, timer, CRUD, circle
  drawer, cells), each as an example and as a test. They are the
  evaluation: a comparison that others can check against their own
  language.
- **How IUP gets into the container** (confirm): a script of the
  repository fetches a fixed version and builds it, or fetches its
  binaries. Nothing of IUP is committed.
- **Documents in English**; talk to the author in Portuguese.

## The first milestone is a check

Nothing else matters if this fails, so it comes alone and first:

- Get IUP into the container, at a fixed version.
- Build a C program that opens a dialog with a button, with no
  screen: a virtual display (`Xvfb`), since GTK needs one.
- Press the button from the program, and take a screenshot.

If any of the three cannot be done (the network does not reach the
downloads, a package is missing and cannot be installed, the virtual
display does not work), stop and tell the author what failed and what
was tried. Do not replace IUP by another toolkit on your own.
Installing packages needs his permission.

## Design

- **Events**: a callback of IUP becomes an event with the handle of
  its control, as in `lua-atmos/env-iup`:
  `await :action [h=btn]`. The tags have no prefix: the author
  decided it for all environments on 2026-11-13. One generic callback in C serves every
  control: it finds the handle and the name of the callback, and
  emits.
- **Callbacks that return a value** (a close that may be refused, a
  key that may be ignored) do not fit an event, which returns
  nothing. Find them, and decide one rule (the program sets what the
  callback will return before it happens).
- **A handle is a native value.** A dialog pinned in a block is
  destroyed when the block ends: a dialog that lives while a task
  lives. IUP destroys the children of a dialog with it: the
  finalizers of the children must not destroy twice.
- **The loop**: the environment defines `main` and runs the loop of
  IUP, one step at a time, and lets the time of the program pass, so
  that `await 1s` works.
- **A test mode**, as the other environments have: with no person,
  a script of actions at given times (press this button, set this
  value), a trace, and screenshots.

What a program may look like (a sketch, not compiled):

```
val txt = iup.text [value="0", readonly="YES"]
val btn = iup.button [title="Count"]
pin dlg = iup.dialog [title="Counter", iup.hbox [txt, btn]]
iup.show(dlg)

watching :close [h=dlg] {
    loop n on :action [h=btn] {
        iup.set(txt, "VALUE", n + 1)
    }
}
```

## Fidelity

- There is no original to compare with: the tests are traces and
  screenshots of the examples under a script of actions.
- Screenshots of native controls depend on the theme and the fonts of
  the system. Fix them in the test mode, and compare a screenshot only
  where the pixels are stable; else compare the values of the
  attributes.
- The address sanitizer (`ATMOS_ASAN=1`) on every test. GTK reports
  leaks of its own: say how they are told apart.

## What the other ports taught

Read "What the Pingus port taught" in `ia-atmos/lang`,
`.claude/plans/261111-snkrx.md`. For an environment in particular:

- **A native literal fails by assigning to `st`**:
  `` `if (h == NULL) { st = a_error("invalid class"); }` ``. Never
  `return` out of one.
- **The names with the prefixes `a_`, `A_`, and `atm_` are
  reserved.** Give every name of the prelude a prefix of your own.
- **At the end**: `atm_stop()`, then `atm_quit()` (the finalizers
  run), and only then `IupClose()`.
- **A task spawned in the body of a loop, of an `if`, or of a branch
  of `match` is aborted when that block ends.** What lives longer goes
  to a pool of its owner, or is pinned outside.
- **A pinned value cannot be stored in a table that is an argument**:
  `iup.hbox [txt, btn]` with `txt` pinned is an error. So the controls
  inside a dialog are not pinned, and only the dialog is. This shapes
  the whole interface: check it in the first example.
- **The time passes in pieces**: a `:clock` await awakes at each timer
  that expires.

## What the port may need from the compiler

Report to the session of the compiler, with a small program:

- A modal dialog: while it is open, the rest of the program must not
  react to the keyboard and the mouse. The language has `toggle`; the
  author has an open proposal for a `grab` (issue 22 of
  `atmos-lang/atmos`). A real case from here helps that decision.
- A callback that must return a value.
- Constructors with pinned values inside (the item above).

## Risks

- **Getting and building IUP**, and a display with no screen. The
  first milestone exists for this.
- **The Mac.** If IUP has no driver for it, the environment is for
  Linux and Windows. Verify, and say so in the readme.
- **Two environments in one program**: a GUI with the network needs
  two loops. The session `uv` (`ia-atmos/env-uv`) meets the same
  question; the design is the author's.
