# pico-1oom: Master of Orion in Atmos, one to one

Initial instructions for the repository `ia-atmos/pico-1oom`, session
`pico-1oom`. Written in the session that maintains the compiler
(`ia-atmos/lang`). The author commands this port himself, in its
session: this is where it starts from, not a schedule.

## Context

- 1oom reproduces the DOS game Master of Orion (Simtex, MicroProse,
  1993) in C, for current systems. The repository is a fork of it.
- The port is to Atmos, over the compiler `ia-atmos/lang` (branch
  `main`; read `doc/manual.md` there before writing code) and, by the
  name of the repository, over the environment of pico
  (`ia-atmos/env-pico`).
- **First one to one, with fidelity.** The first version follows the
  C as it is: the same modules, the same functions, the same order of
  operations, with the same results. It is not rewritten in the style
  of the language yet.
- Only when it is fully faithful may it be made more expressive, as
  long as the intent of the original is not affected. This is a rule
  of the author for every port (2026-11-14).
- It differs from the other ports: a game of turns, of strategy, with
  no physics and no frames of animation in its logic. What it has is
  a large state, long sequences of screens and dialogs, and an
  artificial opponent.

## Three things to know before anything

1. **The project forbids code made by AI.** Its readme says: "Direct
   use of AI-generated code is prohibited in 1oom." This port lives
   in a fork and is another work, under the same license (GPL-2),
   which allows it. But nothing made here goes back to the original
   project: no pull request, no issue, no patch. The readme of this
   repository must say, at its top, that it is a port to Atmos made
   with AI, not affiliated with 1oom. The author decides whether to
   go on in view of that rule: ask him first.
2. **The game needs data that is not free.** 1oom requires the LBX
   files of Master of Orion v1.3, from an original copy that one must
   own (their checksums are in `doc/lbxmd5.txt`). They cannot be
   fetched, and must never be committed. Nothing runs without them,
   so no fidelity can be checked until the author provides them to
   the session.
3. **The branch.** The fork has only `master`, whose readme says that
   this version is no longer developed and points to a branch
   `vanilla` of the original, which the fork does not have. Which
   version to port is the author's to say. The default branch here is
   `master`, not `main`.

## What the target is made of

78 thousand lines of C (`src/`, with headers), at `42e9c0b`.

| Part | Where | Lines | Note |
|------|-------|-------|------|
| The logic of the game | `src/game/`, 35 files | 28013 | It knows nothing about the hardware. The largest: the classic AI (4511), the battle played by a person (2128), the turn (1806), a new game (1225), events (1174), saves (1096), the audience (1070) |
| The interface of 1993 | `src/ui/classic/`, 55 files | 24673 | Screens, dialogs, the battle. The largest: the objects of the interface (2403), the battle (2013), the design of ships (1295) |
| A textual interface | `src/ui/cmdline/`, 34 files | 6094 | A proof of concept: the game played by commands on the standard input |
| Formats and utilities | `src/` | 14067 | LBX, fonts, palette, music, configuration, the tools |
| The hardware | `src/hw/` (SDL 1, SDL 2, Allegro, none) and `src/os/` | 5275 | Video (a buffer of 320x200 with a palette), mouse, keyboard, audio |

The layers are kept apart, and their borders are small (from
`HACKING`): the logic does not know the hardware; the hardware does
not know the logic nor the interface; the interface knows all of the
logic. The borders are three headers: `src/hw.h` (75 lines),
`src/ui.h` (195), and `src/gameapi.h` (13).

## What makes fidelity checkable

- **A game is reproducible from a seed**: `-new GAMESEED` starts a
  game from a seed that fixes the options, the races, and the galaxy.
- **The saved game is the whole state**, in a documented format
  (`doc/format_save.txt`), and a tool converts it to text
  (`1oom_saveconv`). So the oracle is direct: from the same seed and
  the same commands, the C and the port must write the same save,
  byte by byte, turn after turn.
- **The textual interface runs with no screen**, from commands on the
  standard input. With the hardware `nop`, the logic can be driven
  and compared with no window at all.
- For the interface of 1993, the screen is a buffer of 320x200 with a
  palette: its checksum per frame, under scripted input, is the
  oracle, as in the port of Doom.

## Questions that the port must answer early

Not decided here. They are the author's, in the session.

- **Where the state lives.** The game is one large C structure
  (`struct game_s`), which every module reads and writes, and which
  the save writes field by field. One to one, it either stays in C,
  with the Atmos code reaching it through accessors, or becomes
  Atmos tables, with the save rewritten. The first allows the port to
  go module by module with the rest still in C; the second does not.
- **The order.** C cannot call a function of Atmos; Atmos calls C.
  So a port in steps goes from the top down: the sequence of a turn
  and the flow between screens first, calling what is still in C
  below. The leaves (the formulas, the AI) come last, or stay.
- **What goes over pico.** The hardware of 1oom is a buffer with a
  palette that the game draws into by itself. Over pico, either that
  buffer is shown as one image per frame (one to one, and small), or
  the drawing is redone with the operations of pico (another game to
  the eye of a test).
- **What is ported at all.** The tools (`lbxview`, `lbxedit`,
  `pbxmake`, `saveconv`), the textual interface, and the three
  hardware backends are candidates to stay out.

## What the other ports taught

Read "What the Pingus port taught" in `ia-atmos/lang`,
`.claude/plans/261111-snkrx.md`: ten items, of which the first three
decide the result (the original with a trace from day one; a test
mode with no screen; numbers as the original). Since then:

- **A task spawned in the body of a loop, of an `if`, or of a branch
  of `match` is aborted when that block ends**, silently: the most
  common mistake of the ports. What lives longer goes to a pool of
  its owner, or is pinned outside (`pin t = if c { spawn T() }`).
- **The order of awaking is in the manual.**
- **`await(n, :e)`** awaits the nth occurrence of a pattern.
- **A pinned value cannot be stored in a table of a module, nor in a
  table that is an argument or a pattern.** The rules of `pin` are
  under discussion by the author.
- **Integers and reals are distinct** (64-bit integers; `7 // 2` is
  `3`, `7 / 2` is `3.5`), and indexes start at 0, as in C. The C of
  the game uses 8, 16, and 32-bit integers that wrap around: where
  the original depends on the width, the port must reproduce it.
- **C that the program calls may emit into the program**; a native
  literal fails by assigning to `st`; the names with the prefixes
  `a_`, `A_`, and `atm_` are reserved.

## Risks

- **The rule of the original project on AI**, and the data that
  cannot be distributed: see above. Both may stop the port before it
  starts.
- **The size.** 78 thousand lines, one to one, is the largest port so
  far (Pingus and the slice of SuperTux are smaller). A slice must be
  chosen: the logic of a turn with the textual interface is a
  complete game with no screen.
- **A one to one port may show little of the language.** A game of
  turns written as functions over a structure stays that way when
  translated. What the language adds is in the sequences of the
  interface (screens, dialogs, the phases of a turn, the battle),
  which only shows after fidelity, when the code may change.
- **The width of the integers**, in the formulas and in the random
  generator: one wrap that differs changes the whole game.
