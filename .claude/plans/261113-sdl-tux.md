# sdl-tux: SuperTux in Atmos

Plan for the repository `ia-atmos/sdl-tux`, session `sdl-tux`.
Written in the session that maintains the compiler (`ia-atmos/lang`).
First drafted on 2026-11-11 and put aside; taken up again on
2026-11-13, with what four ports taught since.

## Context

- SuperTux is a free 2D platform game (GPL-3, free art) in C++17, over
  SDL2 and OpenGL. It is the best known free game of its kind.
- This plan ports a slice of it to Atmos, over the compiler
  `ia-atmos/lang` (branch `main`; read `doc/manual.md` there before
  writing code), in the repository `ia-atmos/sdl-tux`.
- It follows the port of Pingus (`ia-atmos/sdl-pingus`, plan in
  `261110-pingus.md` of the compiler), with three differences:
    - There is no Céu rewrite to follow: the port is made straight from
      the C++, and the patterns of the Pingus study are applied to code
      that never had them.
    - The original is modern C++ with good performance, so the
      benchmark is harder than the one of Pingus.
    - The original embeds a second language, Squirrel, for what C++
      does not say well: "do this, wait two seconds, do that". Its
      scripts are coroutines that wait. In Atmos that is the language
      of the game itself: see Scripts.
- Goals, in order:
    1. Behavior written as sequences: one task per enemy, object, and
       phase of the player, with the patterns of the Pingus study.
    2. No state variables for control: no state enums, flags, or timers
       that only say where the code is.
    3. The data of the game as Atmos data, read with `X.load`.
    4. The same game, tick by tick, as the official one, in what is
       ported.
    5. Memory and CPU near the official game.

## Scripts

Measured on the tag:

| | World 1 | The whole game |
|---|---|---|
| Levels | 31 | 110 |
| Scripts embedded in the levels | 188 | 683 |
| Lines of those scripts | 490 | 2528 |
| Typical size | 1 line (at most 41) | 1 line (at most 61) |
| Files of scenes (`.nut`) | 7 files, 1375 lines | not counted |

- Most are one line in a trigger: `torch1.set_burning(true)`,
  `lift2.start_moving()`, `secret1_cover.fade(0, 1)`. The function
  called most is `wait(n)`, 324 times.
- For this the C++ carries a virtual machine, a scheduler of
  coroutines (`src/squirrel/`, 1477 lines), and 474 functions exposed
  to the scripts, in 79 files. World 1 uses 137 distinct calls.
- The author asked: must the game be recompiled for a new level? If a
  script becomes Atmos code, yes, since Atmos has no load of code at
  run time. In the original nothing recompiles: that is what the
  Squirrel is there for.

So, as recommended to the author then (to confirm, see below):

- **The scripts embedded in the levels become data**, inside the file
  of the level, which a small task interprets:

  ```
  script = [
      [:call, "torch1", :set_burning, true],
      [:wait, 2.2],
      [:call, "Effect", :fade_out, 2],
  ]
  ```

  A `:wait` is an `await`, and a `:call` goes to the object by its
  name. The converter translates the Squirrel. A level stays data, and
  a new level does not recompile the game.
- **The long scenes** (the seven `.nut` files of World 1, with
  functions and conditionals, which are part of the game and not of a
  level) become Atmos code, compiled with the game.
- **The limit**: a script of a third party with logic of its own does
  not run, unless the converter learns that part.
- **What it shows**: the interpreter of scripts is a task of a few
  dozen lines, because to wait is already in the language. Measure
  what disappears: the virtual machine, the scheduler, the functions
  of binding.

## Patterns

The five patterns of the Pingus study, as they show in SuperTux:

| Pattern | In SuperTux |
|---------|-------------|
| Finite state machine | `MrIceBlock` (normal, flat, kicked, grabbed, waking), the player (small, big, fire, ducking, sliding, dying) |
| Continuation passing | the end sequence of a level, cutscenes, the worldmap after a level |
| Dispatching hierarchy | `Sector::update` and `draw` over all objects, by layer |
| Lifespan hierarchy | sector, objects, bullets, particles, the coin that leaves a block |
| Signaling | squished, kicked, hit by bullet, player hurt, block bumped from below |

- An enemy is a task. Its states are its code in sequence: a
  `watching` for what ends a state, an `await` for what it waits.
- A `Timer` member becomes an `await` of ticks.
- What lives for a while (a bouncing coin, an explosion, a squished
  sprite) is a task spawned in the block that owns it.

## State variables

Rules, as in the Pingus port, with a table kept in `doc/state.md`:

- Not allowed: an enum or flag that says in which phase the code is, a
  counter of frames or ticks kept across calls, a timer checked every
  tick.
- Allowed: positions, velocities, and other physical quantities; the
  inventory of the player; what the HUD shows.
- Every state variable of the C++ that the port covers is listed with
  what became of it.

## Data format

- A converter (`tools/convert.py`) from s-expressions to Atmos data,
  as in Pingus: levels, sprites, tilesets, worldmaps.
- Tilemaps are large arrays of numbers: measure `X.load` on the
  largest level early. If it is slow, the tiles go to a packed string
  or a binary file read in C.
- The scripts embedded in the levels are converted to data (see
  Scripts). The converter says, for each script it cannot translate,
  where it is and why.

## Fidelity

The Pingus port went from 39 to 142 of 154 demos with the same trace
only after it compared tick by tick with the official game. So this
is set up before the first enemy is written:

- Build the official game at `v0.7.0` in the container (`--renderer
  sdl`, dummy video driver).
- Patch it (`tools/bench/official.patch`) to:
    - read scripted input by tick (left, right, jump, action, down);
    - fix the random seed;
    - print a trace: per tick, the position, velocity, and state of
      the player; per event, each enemy that changes state or dies.
- The port prints the same trace (`TUX_TRACE`) from the same script.
- `tools/compare.sh` runs both and shows the first tick that differs.
- A set of scripted runs per level (walk right, jump on each enemy,
  die in each way) is the regression suite.
- Floats: the official game uses 32-bit floats. The port needs the
  same arithmetic where positions are compared (in Pingus, the mover
  went to C for this).

## Benchmark

- Baseline: the official game at `v0.7.0`, release build, `--renderer
  sdl`, in the same container, one after the other.
- Measure: peak memory, CPU in 10 s at the frame cap, frames in 10 s
  with no cap, time to the first frame of a level, size of the binary,
  lines and tokens of what was ported against its C++.
- Scenarios: the menu; the first level with no input; the largest
  level of World 1; a level with 200 enemies made for the test.
- In Pingus, the port used 1.05x the memory and the same CPU, and drew
  0.8x the frames with no cap, with a fixed cost per frame. This port
  starts over the compiler with trails, so it should not be worse.

## What the other ports taught

Read "What the Pingus port taught" in `261111-snkrx.md` of the
compiler: ten items, sent by the session of that port, which hold for
any port. The first three decide the result: the official game with a
trace from day one; a test mode with no screen in the port; numbers
as the original (32-bit floats, the order of objects, the phases of
an update).

Since then, from SNKRX, Flare, Lessmilk, and the raylib games:

- **A task spawned in the body of a loop, of an `if`, or of a branch
  of `match` is aborted when that block ends**, silently. It was the
  most common mistake of the ports (29 places in one of them). What
  lives longer goes to a pool of its owner (`pin fx = tasks()`), or
  is pinned outside: `pin t = if c { spawn T() }`.
- **The order of awaking is in the manual**: the tasks of a block in
  the order they were attached; nested tasks and pools before the
  body of the task that holds them; a task only reacts to an emit
  that starts after its await.
- **`await(n, :tick)`** awaits the nth occurrence (`watching n, :e
  {...}`, `loop on n, :e {...}`): the game advances in ticks of 15
  ms, and its `Timer` members become this.
- **A `:clock` await awakes at each timer that expires**, many times
  per frame: what runs once per tick awaits the event of the tick.
- **A loop over a pool tolerates aborts and spawns in its body.**
- **A pinned value cannot be stored in a table of a module, nor in a
  table that is an argument.** Keep one pinned context in the block
  of the pool and pass it as one argument.
- **Building small tables is the cost that shows** in the profiles of
  three ports (about 0.5 us each): no table per pair in a collision
  pass, and no table per tile.

## What the port may need from the compiler

Report to the session of the compiler, with a small program, and
keep `doc/compiler.md`. Candidates known from the other ports:

- An await over a pool with a condition ("a pingu enters my zone").
- Phases inside a tick, instead of spawn order.
- 32-bit float arithmetic in Atmos.
- A shorter build for the edit and run loop.

## Risks

- **Size.** The slice is still large: 28 enemies and 32 objects in
  World 1. The first version is cut to ten enemies and five levels so
  that there is a complete result early.
- **Collisions.** The collision system is the core, and the one part
  where a direct translation of the C++ would bring back the polling.
- **Fidelity with floats.** Positions are floats integrated every 15
  ms: one rounding off diverges a whole run.
- **Scripts.** The converter must translate the Squirrel of the
  levels to data. The scripts of World 1 are almost only calls and
  waits; one that is not needs the author's decision, not a silent
  workaround.
- **The environment is being written at the same time**, by another
  session, for three other games. What Tux needs may not be there
  when it needs it: ask early.
- **Performance.** The official game is fast. A level with hundreds
  of tiles and objects on screen must not cost a task per tile.
