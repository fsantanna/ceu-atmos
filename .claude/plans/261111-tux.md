# Plan: SuperTux in Atmos

Status: draft, not yet sent to the session that will execute it.

## Context

- SuperTux is a free 2D platform game (GPL-3, free art) in C++17, over
  SDL2 and OpenGL. It is the best known free game of its kind.
- This plan ports a slice of it to Atmos, over this compiler
  (`fsantanna/ceu-atmos`), in the session `tux`, in the repository
  `fsantanna/ceu-atmos-tux`.
- It follows the port of Pingus (`fsantanna/ceu-atmos-pingus`, plan in
  `261110-pingus.md`), with two differences:
    - There is no Céu rewrite to follow: the port is made straight from
      the C++, and the patterns of the Pingus study are applied to code
      that never had them.
    - The original is modern C++ with good performance, so the
      benchmark is harder than the one of Pingus.
- Goals, in order:
    1. Behavior written as sequences: one task per enemy, object, and
       phase of the player, with the patterns of the Pingus study.
    2. No state variables for control: no state enums, flags, or timers
       that only say where the code is.
    3. The data of the game as Atmos data, read with `X.load`.
    4. The same game, tick by tick, as the official one, in what is
       ported.
    5. Memory and CPU near the official game.

## Settled decisions

To confirm with the author before the work starts (see the questions
sent with this plan):

- **Repository**: `fsantanna/ceu-atmos-tux`, commits straight to
  `main`, in small grains.
- **Target**: the tag `v0.7.0`.
- **Slice**: World 1, in two steps (see Scope).
- **Scripts**: no Squirrel. The scripts of the levels in the slice are
  rewritten by hand as Atmos tasks, next to the converted level.
- **Renderer**: SDL2 only, no OpenGL, no shaders. Lights are out of
  the first version.
- **Engine**: one C header over SDL2 (as `engine/pingus.h`): images,
  fonts, sounds, tile drawing, and the geometry of collisions. The
  logic of collisions, and everything else, in Atmos.
- **Language**: English only in the first version.

## Patterns

The five patterns of the Pingus study, as they show in SuperTux:

| Pattern | In SuperTux |
|---------|-------------|
| Finite state machine | `MrIceBlock` (normal, flat, kicked, grabbed, waking), the player (small, big, fire, ducking, sliding, dying) |
| Continuation passing | the end sequence of a level, cutscenes, the worldmap after a level |
| Dispatching hierarchy | `Sector::update` and `draw` over all objects, by layer |
| Lifespan hierarchy | sector, objects, bullets, particles, the coin that leaves a block |
| Signaling | squished, kicked, hit by bullet, player hurt, block bumped from below |

- An enemy is a task. Its states are its code in sequence: a
  `watching` for what ends a state, an `await` for what it waits.
- A `Timer` member becomes an `await` of ticks.
- What lives for a while (a bouncing coin, an explosion, a squished
  sprite) is a task spawned in the block that owns it.

## State variables

Rules, as in the Pingus port, with a table kept in `doc/state.md`:

- Not allowed: an enum or flag that says in which phase the code is, a
  counter of frames or ticks kept across calls, a timer checked every
  tick.
- Allowed: positions, velocities, and other physical quantities; the
  inventory of the player; what the HUD shows.
- Every state variable of the C++ that the port covers is listed with
  what became of it.

## Data format

- A converter (`tools/convert.py`) from s-expressions to Atmos data,
  as in Pingus: levels, sprites, tilesets, worldmaps.
- Tilemaps are large arrays of numbers: measure `X.load` on the
  largest level early. If it is slow, the tiles go to a packed string
  or a binary file read in C.
- Scripts are not converted: they are rewritten by hand, and the
  converter only keeps where each one was.

## Scope

### First version: a level, complete

- The player: walk, run, jump, duck, skid, grow, fire flower, hurt,
  die, the end sequence.
- Tilemaps with solid, slope, and unisolid tiles; the collision
  system; the camera.
- Coins, bonus blocks, bricks, powerups, spawnpoints, the HUD.
- The ten most used enemies of World 1: snowball, jumpy, stalactite,
  mriceblock, smartball, mrbomb, flyingsnowball, bouncingsnowball,
  spiky, fish-swimming (2164 lines in C++, plus the base).
- Platforms on paths, weak blocks, unstable tiles.
- The first five levels of World 1, from start to end.
- A test mode with no screen, scripted input, and a trace.

### Second version: World 1

- The other 18 enemies and the remaining objects of World 1.
- The worldmap, the menu, the save of the progress.
- The yeti boss and the cutscenes, with their scripts as tasks.
- Lights, with the SDL renderer, if they are cheap.

### Out

- The editor, the add-ons, the Squirrel machine, the console.
- The other worlds, multiplayer, controllers.
- OpenGL, shaders, the translations.

## Fidelity

The Pingus port went from 39 to 142 of 154 demos with the same trace
only after it compared tick by tick with the official game. So this
is set up before the first enemy is written:

- Build the official game at `v0.7.0` in the container (`--renderer
  sdl`, dummy video driver).
- Patch it (`tools/bench/official.patch`) to:
    - read scripted input by tick (left, right, jump, action, down);
    - fix the random seed;
    - print a trace: per tick, the position, velocity, and state of
      the player; per event, each enemy that changes state or dies.
- The port prints the same trace (`TUX_TRACE`) from the same script.
- `tools/compare.sh` runs both and shows the first tick that differs.
- A set of scripted runs per level (walk right, jump on each enemy,
  die in each way) is the regression suite.
- Floats: the official game uses 32-bit floats. The port needs the
  same arithmetic where positions are compared (in Pingus, the mover
  went to C for this).

## Benchmark

- Baseline: the official game at `v0.7.0`, release build, `--renderer
  sdl`, in the same container, one after the other.
- Measure: peak memory, CPU in 10 s at the frame cap, frames in 10 s
  with no cap, time to the first frame of a level, size of the binary,
  lines and tokens of what was ported against its C++.
- Scenarios: the menu; the first level with no input; the largest
  level of World 1; a level with 200 enemies made for the test.
- In Pingus, the port used 1.05x the memory and the same CPU, and drew
  0.8x the frames with no cap, with a fixed cost per frame. This port
  starts over the compiler with trails, so it should not be worse.

## Tests

- `ASAN=1 tst/run.sh`: the same with the address sanitizer.
- `tools/compare-all.sh`: every scripted run against the official

## What the Pingus port taught

The list its session sent, in its order of importance. It holds for
any port of this kind, whatever the game.

1. **Day one: the official game with a trace.** Build it and patch it
   to print a trace in the exact format of the port (time, object,
   state, x, y), flushed, plus a dump per tick of one chosen object,
   plus a replay of its recordings faster than real time, with no
   screen. Reading the C++ found 3 differences; the traces found about
   15. Fidelity went from 17 to 142 identical demos only after the
   first differing tick could be found. Check early that the official
   game builds in the container (installing packages needs the
   author's permission).
2. **Day one too: a test mode with no screen in the port.**
   Environment variables for the frames to run, scripted input by
   tick, a screenshot at a frame, mute, no frame cap, the frame count
   at exit. Every test, replay, and benchmark used it. Stored traces
   per level caught every regression.
3. **Numbers as the original.** The same float width from the start
   (C++ `float` is 32 bits, Atmos numbers are doubles): there, the
   mover went to C. Also: the real positions of objects (the converter
   rounded them), the order of objects at setup, the two phases of an
   update (move, then react), when input applies inside a tick, and
   forced against requested changes of state. Copy the clocks of the
   official code exactly.
4. **Scope decided up front.** The plan said one thing and the author
   then wanted all the official data and objects. Put the later items
   in the main milestones. A generic converter from s-expressions,
   with a list of kinds, was easy.
5. **Engine.** A single C header (about 900 lines there: image cache,
   fonts, sounds, collision maps, mover) plus thin wrappers in Atmos,
   and one C file to build (24 s at `-O2`). Hot pixel loops and exact
   float math go to C. Sprite descriptions are cached, never loaded
   per frame.
6. **Idioms that worked.** One task per entity, whose life is the
   task; a pool per draw layer (draw order is pool order); the state
   machine of an entity as a `loop` over `par :any { action } with {
   orders } with { forced }`, whose result is the next state;
   `watching` for phases that can be aborted; `toggle` for pause;
   `await Ticks(n)` for clocks; `do :tag { escape :tag }` for
   continue.
7. **Pitfalls.** `emit @:parent` from a task in a pool reaches the
   pool, not its owner: pass the receiver. A spawn inside an `if`
   block dies with the block. Iterating a tagged table gives its
   `tag`. A sprite of one frame that never ends leaks into its pool
   (it made the rain quadratic there). In `main` since then:
   `[loop=false]`, `"a\"b"`, and the error for a nested `func`.
8. **What still reads poorly there.** Objects that scan a whole pool
   every tick; the order inside a tick carried by spawn order and two
   events; records of an entity written from outside; animation clocks
   derived by arithmetic. For a game with collisions everywhere,
   decide early how they are dispatched: one broad phase in C per
   tick, which emits events to the tasks involved, rather than each
   task scanning.
9. **Environment.** The official game needed about 15 development
   packages and a few minutes to build. Its suite takes about a
   minute; comparing 159 demos, 15 to 20 minutes with 4 jobs. Heavy
   runs go to the background, and the benchmark runs alone (the noise
   is about 10% anyway). The official checkout stays outside the
   repository, and its patch inside.
10. **With the author.** Small commits, each pushed, straight to
    `main`. Design and fidelity decisions were settled alone and
    written down. What needed the author: installing packages, scope
    beyond the plan, and what to do next. Only measured numbers go
    into the documents.

## What the port may need from the compiler

Report in `doc/compiler.md`, as the Pingus port did. Candidates known
from Pingus:

- An await over a pool with a condition ("a pingu enters my zone").
- Phases inside a tick, instead of spawn order.
- 32-bit float arithmetic in Atmos.
- A shorter build for the edit and run loop.

## Risks

- **Size.** The slice is still large: 28 enemies and 32 objects in
  World 1. The first version is cut to ten enemies and five levels so
  that there is a complete result early.
- **Collisions.** The collision system is the core, and the one part
  where a direct translation of the C++ would bring back the polling.
- **Fidelity with floats.** Positions are floats integrated every 15
  ms: one rounding off diverges a whole run.
- **Scripts.** Levels depend on Squirrel scripts. Rewriting them by
  hand works for World 1, and does not scale to the other worlds.
- **Performance.** The official game is fast. A level with hundreds
  of tiles and objects on screen must not cost a task per tile.

## Workflow

- Commits straight to `main`, small, each with its test.
- Decisions that belong to the author are asked one at a time, with a
  recommended option.
- Findings in the compiler are reported, not worked around in
  silence.
