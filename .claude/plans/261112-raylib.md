# Plan: the raylib games in Atmos

Status: sent to the session `raylib`, which executes it in the
repository `ia-atmos/env-ray`.

## Context

- raylib is a small C library to write games. Its author keeps a
  collection of games made with it, `raysan5/raylib-games`: twelve
  classics of the arcade, each in one file, and eleven games made for
  game jams and for release, with art and sound.
- They are the common shape of a small game in C: global state, a
  counter of frames, flags such as `gameOver` and `pause`, and one
  function that updates everything every frame.
- This plan ports all 23 to Atmos, over the compiler
  `ia-atmos/lang` and over raylib itself, so that the original
  and the port use the same library.
- It follows the ports of Pingus (complete), SNKRX, and Flare (both
  in course). Those are one large game each. This is the opposite:
  many small games, of several genres, each one finished in hours,
  and a table that compares them one by one.
- Goals, in order:
    1. An environment for raylib in Atmos, reusable by any program.
    2. Behavior written as sequences: every count of frames and every
       flag that guards a phase becomes an `await` or a block.
    3. The same game: the same screens at the same frames, with the
       same seed and the same input.
    4. A table per game: lines, tokens, state variables removed,
       memory, and CPU, against the C.

## Settled decisions

The author asked for this plan and decided: all the games, and
raylib on both sides. The items marked "(confirm)" are
recommendations that he has not answered: ask, one at a time, before
building on them.

- **Repository**: `ia-atmos/env-ray`, commits straight to `main`, in
  small grains.
- **All in raylib**: the port draws, plays sound, and reads input
  through raylib, as the original. No SDL.
- **All 23 games**, including the one in 3D and the one with a shader:
  raylib gives both.
- **A second user of the environment**: the port of the Lessmilk
  games (`ia-atmos/ray-lessmilk`, plan in `261112-lessmilk.md`) uses
  `raylib.atm` too. The two sessions talk directly about it.
- **The environment** is a file `raylib.atm` in the repository of the
  port, in the shape of `lib/sdl.atm`: a `:prelude` with the driver
  and thin wrappers, and a table with the functions. When it is
  stable, it is offered to `ceu-atmos` as `lib/raylib.atm`.
- **Assets** (confirm): not copied. The port reads them from a
  checkout of `raylib-games` next to it, since their license is not
  stated. The alternative is to ask the author of raylib.
- **Order** (confirm): the classics first, from the smallest; then
  the others, from the smallest, ending in `koala_seasons`.
- **One program per game**, as the original, plus one launcher that
  lists them.

## The environment

- Events emitted by the driver, once per frame, in this order: input
  events (key and mouse, down and up), the time passed (a number, as
  every Atmos environment), then `:draw`.
- Polling stays available (`IsKeyDown` and the like) for what is a
  level, not an event: a key held to move.
- The driver calls `BeginDrawing` before `:draw` and `EndDrawing`
  after it. Tasks draw when they receive `:draw`, in the order they
  were spawned: the order of the pools is the order of the layers.
- Wrappers are thin: one native call each, with the types of raylib
  (vectors, rectangles, colors) as Atmos tables or as native boxes
  where they are resources (textures, sounds, fonts, models,
  shaders), released by their `pin`.
- A test mode with no screen, as in `lib/sdl.atm`: frames to run with
  a fixed time step, scripted input by frame, screenshots at chosen
  frames, a fixed seed, no frame cap, the frame count at exit.

## Patterns

What the C does, and what it becomes:

| Original | Atmos |
|----------|-------|
| `framesCounter++` and `if (framesCounter > n)` | `await` of the time, or of `n` frames |
| `gameOver`, tested at the top of `UpdateGame` | the game is a task that ends; what follows awaits it |
| `pause`, tested around the logic | `toggle` on the task of the game |
| an enum of screens and a `switch` in update and in draw | a task per screen, awaited in sequence |
| a transition that counts and fades between screens | `await Fade(...)` between two awaits |
| an array of entities with an `active` flag | a pool of tasks |
| "press ENTER to play again" as a flag reset | a `loop` around the game |
| `UpdateGame` and `DrawGame`, split, sharing globals | one task per thing, which updates and draws itself |

- The five patterns of the Pingus study apply. With so many small
  games, each pattern gets many short examples.
- A count of frames that only produces a visual effect (a blinking
  text) is also a sequence: a task that toggles and awaits.

## State variables

- A table per game in `doc/state.md`: every global and flag of the C,
  with what became of it.
- Allowed: positions, scores, lives, and what is drawn.
- The summary table counts, per game, the control variables of the C
  and the ones left in the port.

## Fidelity

The games are deterministic once the seed, the input, and the time
step are fixed. Set up before the first game:

- raylib built in the container, in the mode with no screen.
- The original games built against it, with a small patch
  (`tools/original.patch`), the same for all: a fixed seed, a fixed
  time step, scripted input by frame, screenshots at chosen frames,
  and a line of trace per frame with the score and the state that
  each game exposes.
- The port runs the same script and seed.
- `tools/compare.sh` compares the screenshots pixel by pixel and the
  traces line by line, and shows the first frame that differs.
- The port must call the random generator in the same order as the
  original. Where it cannot, say so in `doc/fidelity.md` for that
  game, and compare what remains.
- Positions are 32-bit floats in raylib: the same arithmetic where
  positions are compared.

## Benchmark

- Baseline: each original, release build, in the same container, one
  after the other, in the mode with no screen.
- Measure, per game: peak memory, CPU in 10 s at 60 frames per
  second, frames in 10 s with no cap, size of the binary, lines and
  tokens against the C.
- A stress case in a few games, made for the test: thousands of
  entities (asteroids, invaders, cells of `raylife`).
- The C games are tiny and tight: expect the port to cost more per
  frame. The point is to know how much, game by game.

## What the Pingus port taught

The list its session sent, in its order of importance. It holds for
any port of this kind, whatever the game.

1. **Day one: the official game with a trace.** Build it and patch it
   to print a trace in the exact format of the port (time, object,
   state, x, y), flushed, plus a dump per tick of one chosen object,
   plus a replay of its recordings faster than real time, with no
   screen. Reading the C++ found 3 differences; the traces found about
   15. Fidelity went from 17 to 142 identical demos only after the
   first differing tick could be found. Check early that the official
   game builds in the container (installing packages needs the
   author's permission).
2. **Day one too: a test mode with no screen in the port.**
   Environment variables for the frames to run, scripted input by
   tick, a screenshot at a frame, mute, no frame cap, the frame count
   at exit. Every test, replay, and benchmark used it. Stored traces
   per level caught every regression.
3. **Numbers as the original.** The same float width from the start
   (C++ `float` is 32 bits, Atmos numbers are doubles): there, the
   mover went to C. Also: the real positions of objects (the converter
   rounded them), the order of objects at setup, the two phases of an
   update (move, then react), when input applies inside a tick, and
   forced against requested changes of state. Copy the clocks of the
   official code exactly.
4. **Scope decided up front.** The plan said one thing and the author
   then wanted all the official data and objects. Put the later items
   in the main milestones. A generic converter from s-expressions,
   with a list of kinds, was easy.
5. **Engine.** A single C header (about 900 lines there: image cache,
   fonts, sounds, collision maps, mover) plus thin wrappers in Atmos,
   and one C file to build (24 s at `-O2`). Hot pixel loops and exact
   float math go to C. Sprite descriptions are cached, never loaded
   per frame.
6. **Idioms that worked.** One task per entity, whose life is the
   task; a pool per draw layer (draw order is pool order); the state
   machine of an entity as a `loop` over `par :any { action } with {
   orders } with { forced }`, whose result is the next state;
   `watching` for phases that can be aborted; `toggle` for pause;
   `await Ticks(n)` for clocks; `do :tag { escape :tag }` for
   continue.
7. **Pitfalls.** `emit @:parent` from a task in a pool reaches the
   pool, not its owner: pass the receiver. A spawn inside an `if`
   block dies with the block. Iterating a tagged table gives its
   `tag`. A sprite of one frame that never ends leaks into its pool
   (it made the rain quadratic there). In `main` since then:
   `[loop=false]`, `"a\"b"`, and the error for a nested `func`.
8. **What still reads poorly there.** Objects that scan a whole pool
   every tick; the order inside a tick carried by spawn order and two
   events; records of an entity written from outside; animation clocks
   derived by arithmetic. For a game with collisions everywhere,
   decide early how they are dispatched: one broad phase in C per
   tick, which emits events to the tasks involved, rather than each
   task scanning.
9. **Environment.** The official game needed about 15 development
   packages and a few minutes to build. Its suite takes about a
   minute; comparing 159 demos, 15 to 20 minutes with 4 jobs. Heavy
   runs go to the background, and the benchmark runs alone (the noise
   is about 10% anyway). The official checkout stays outside the
   repository, and its patch inside.
10. **With the author.** Small commits, each pushed, straight to
    `main`. Design and fidelity decisions were settled alone and
    written down. What needed the author: installing packages, scope
    beyond the plan, and what to do next. Only measured numbers go
    into the documents.

## What the port may need from the compiler

Report in `doc/compiler.md`. To watch here:

- The cost of a native call per shape drawn: thousands per frame.
- Vectors and colors as tables, allocated per frame: a cheaper way to
  pass small records to C.
- An environment that ticks in frames as well as in time.
- What `lib/sdl.atm` and `raylib.atm` have in common, to factor out.

## Risks

- **The mode with no screen of raylib.** It is recent. If it does not
  render the same as the desktop platform, the comparisons run under
  a virtual display, which needs packages and the author's
  permission.
- **The order of random calls.** Small games call the generator
  everywhere. A port in tasks may reorder them. The fallback is
  written in Fidelity.
- **Assets.** With no stated license, they are not copied: the port
  depends on a checkout of the original.
- **Performance of drawing.** A task per entity that draws itself
  makes one native call per shape. Measure early with a stress case.
- **Sameness.** Twenty-three small ports may repeat the same idioms.
  The table and one good example per pattern matter more than prose
  for every game.

## Workflow

- Commits straight to `main`, small, each with its test.
- Decisions that belong to the author are asked one at a time, with a
  recommended option.
- Installing packages needs the author's permission: ask at R0.
- Findings in the compiler are reported, not worked around in
  silence. The compiler is maintained by the session `ceu-atmos`.
- Only measured numbers go into the documents.
