# Plan: Flare in Atmos

Status: sent to the session `flare`, which executes it in the
repository `fsantanna/flare`.

## Context

- Flare (Free Libre Action Roleplaying Engine) is a single-player 2D
  action RPG in the style of Diablo, with its game "Empyrean
  Campaign". It is free in full: the engine is GPL-3, and the art and
  data are CC-BY-SA 3.0.
- It is pure C++ (C++98 by choice), over SDL2, with no scripting
  language: the game is defined by text files in the style of INI.
- This plan ports a slice of it to Atmos, over the compiler
  `fsantanna/ceu-atmos` and SDL2 (`lib/sdl.atm`).
- It follows the ports of Pingus (`fsantanna/ceu-atmos-pingus`,
  complete) and SNKRX (`fsantanna/snxkx`, in course). Pingus was C++
  with a Céu rewrite to follow; SNKRX is Lua with timer callbacks.
  Flare is plain C++ with classes that are updated every frame: state
  enums, timers as members, and managers that walk lists.
- Goals, in order:
    1. Behavior written as sequences: one task per entity, power,
       hazard, effect, and screen.
    2. No state variables for control: no state enums, no timers
       checked every frame, no flags that guard a phase.
    3. The data of the game read as it is, or converted once to Atmos
       data read with `X.load`. A new map or enemy never needs a
       rebuild.
    4. The same game in what can be compared: timings, formulas,
       content, and, with a fixed seed, the same events.
    5. Memory and CPU near the original.

| Part | Lines | Files | Note |

| Files, settings, utilities, mods | 8980 | 54 | INI parser, mod manager, translations, save and load |
| Entities (`Entity*`, `Avatar`, `NPC*`, `StatBlock`) | 5827 | 16 | the hero, enemies, allies, stats, behavior |
| Map, collision, camera, fog | 4997 | 16 | isometric renderer, path finding (A*) |
| Widgets | 4584 | 28 | buttons, lists, sliders, slots, tooltips |
| Render, input, sound, fonts | 4562 | 22 | SDL2, software and hardware renderers |
| Game states | 4224 | 16 | title, load, new, play, config, cutscene |
| Powers, hazards, effects | 3576 | 8 | |
| Items, loot | 3446 | 8 | |
| Campaign, events, quests | 2141 | 6 | |
| Animation | 964 | 8 | |

- State kept by hand: an entity has `cur_state` (`ENTITY_STANCE,
  MOVE, POWER, SPAWN, BLOCK, HIT, DEAD, CRITDEAD`), used 83 times;
  there are 34 `Timer` members and 122 enums in the headers.
- `EntityBehavior::logic` runs every frame for every enemy: upkeep,
  find target, check power, check move, update state. Each step tests
  the state and the timers to know where the entity is.
- Powers are of seven types (fixed, missile, repeater, spawn,
  transform, effect, block), with cooldowns, delays, and effects that
  last (`EffectManager`).
- Events of maps are declarative: a list of components (message,
  teleport, spawn, set a status of the campaign, ...) with a way to
  activate (trigger, interact, load, leave, clear) and an optional
  delay and cooldown. `EventManager` has 1476 raw lines.
- The game steps in fixed frames (`max_fps`, 60 by default). Positions
  are 32-bit floats. Chance is used in 106 places, seeded by the time.
- There are no tests, no replays, and no recording of input.

## Settled decisions

The author asked for this plan. The items marked "(confirm)" are
recommendations that he has not answered: ask, one at a time, before
building on them.

- **Repository**: `fsantanna/flare`, commits straight to `main`, in
  small grains.
- **Target**: `flare-engine@56c747a` with `flare-game@af6eee6`.
- **Slice** (confirm): the game screen first, with the `alpha_demo`
  campaign over the art of `fantasycore`; then the Empyrean Campaign.
  Menus are reduced (see Scope).
- **Data** (confirm): read by the port in the original INI format,
  with a reader written in Atmos (or C), so that the original mods
  work unchanged. The alternative is a converter to Atmos data read
  with `X.load`, as in Pingus: faster to load, but the mods must be
  converted.
- **Renderer**: SDL2 only, as the original's software and hardware
  renderers.
- **Engine**: one C header over SDL2 for images, fonts, sounds, the
  isometric drawing of tiles, the collision map, and path finding.
  Everything else in Atmos.
- **Language**: English only in the first version.
- **Fidelity** (confirm): with a fixed seed and scripted input, the
  same trace of events as the original (see Fidelity). This asks for
  the same random generator and 32-bit floats in what moves.

## Patterns

The five patterns of the Pingus study, as they show in Flare:

| Pattern | In Flare |
|---------|----------|
| Finite state machine | `cur_state` of an entity: stance, move, power, hit, dead; the phases of a power (cast, delay, hazard, cooldown) |
| Continuation passing | title, load, play; a dialog with an NPC and what follows; a cutscene; the game over |
| Dispatching hierarchy | `GameStatePlay::logic` and `render` over managers, each over its list |
| Lifespan hierarchy | map, entities, hazards, effects, loot, floating texts: all end with the map, an effect ends with its entity |
| Signaling | hit, death, a status of the campaign set, an event activated, the hero changes level |

What the C++ does, and what it becomes:

| Original | Atmos |
|----------|-------|
| `cur_state` and a `switch` per frame | the body of the task of the entity, in sequence |
| a `Timer` member, ticked and tested every frame | `await` of ticks |
| a cooldown stored per power | `loop { await use ; ... ; await cooldown }` |
| an effect with `duration` and `ticks`, in a list | a task per effect, pinned to its entity |
| a hazard with `lifespan`, in `HazardManager` | a task per hazard, in a pool |
| a manager that walks a list and removes the dead | a pool of tasks |
| a `GameState` with `logic` and `render`, swapped by a switcher | a task per screen, awaited in sequence |
| a menu with `visible` and a click that sets a result | a task that returns the choice |
| an event with `delay` and `cooldown` counters | a task that waits its activation, then awaits |

- The state machine of an entity follows what worked in Pingus: a
  `loop` over `par :any { the current action } with { what interrupts
  it }`, whose result is the next action.
- A hit, a stun, or the death interrupts whatever the entity does:
  one `watching` around the action, not a test in every state.

## State variables

- A table in `doc/state.md`, as in Pingus: every state enum, timer,
  and flag of the C++ that the port covers, with what became of it.
- Allowed: positions, stats, the inventory, the statuses of the
  campaign (they are the save game), and what the HUD shows.
- The statuses of the campaign are state, but of the story, kept in
  data by design. They stay.

## Data format

- INI files are read by a generic reader into tables: a list of
  sections, each with its keys in order. It replaces `FileParser` and
  the parsing code spread over the managers.
- The meaning of each key stays with the task that uses it.
- Maps come from Tiled in the same text format, with layers as lists
  of numbers: measure the load of the largest map early. Keep the tile
  layers in C if tables are slow or large.
- Mods are layered as in the original: a file in a later mod replaces
  or extends the one of an earlier mod.

## Fidelity

The original is deterministic once the seed and the input are fixed:
it steps in fixed frames, and all chance comes from `rand`. So, unlike
SNKRX, the same events can be expected. It is set up before the first
enemy is written:

- Build the original in the container, with the software renderer and
  the dummy video driver.
- Patch it (`tools/bench/original.patch`) to:
    - fix the seed, and use a generator of its own instead of `rand`
      of the C library, so that the port can use the same;
    - read scripted input by frame (mouse position, buttons, keys);
    - print a trace: per event, an entity that changes state, a power
      used, a hit with its damage, a death, loot dropped, an event of
      the map activated; and, on request, one entity per frame;
    - run faster than real time, with a frame count at exit.
- The port prints the same trace from the same script and seed.
- `tools/compare.sh` runs both and shows the first line that differs.
- A set of scripted runs per map and per enemy is the regression
  suite.
- Positions are 32-bit floats in the original: the port moves entities
  with the same arithmetic, in C where needed.
- If the same trace proves out of reach (the order of calls to the
  generator is fragile), fall back to timings, formulas, and
  distributions, and say so in `doc/fidelity.md`.

## Benchmark

- Baseline: the original, release build, software renderer, in the
  same container, one after the other.
- Measure: peak memory, CPU in 10 s at 60 frames per second, frames in
  10 s with no cap, the time of a logic frame with many enemies, time
  to the first frame of a map, size of the binary, lines and tokens of
  what was ported against its C++.
- Scenarios: the title; a map with no input; the largest map; a map
  with 200 enemies made for the test; a fight with many hazards and
  effects.
- In Pingus, the port used 1.05x the memory and the same CPU, and the
  game was dominated by the SDL renderer. Flare has many more entities
  that think every frame, so it tests the runtime more.

## What the Pingus port taught

The list its session sent, in its order of importance. It holds for
any port of this kind, whatever the game.

1. **Day one: the official game with a trace.** Build it and patch it
   to print a trace in the exact format of the port (time, object,
   state, x, y), flushed, plus a dump per tick of one chosen object,
   plus a replay of its recordings faster than real time, with no
   screen. Reading the C++ found 3 differences; the traces found about
   15. Fidelity went from 17 to 142 identical demos only after the
   first differing tick could be found. Check early that the official
   game builds in the container (installing packages needs the
   author's permission).
2. **Day one too: a test mode with no screen in the port.**
   Environment variables for the frames to run, scripted input by
   tick, a screenshot at a frame, mute, no frame cap, the frame count
   at exit. Every test, replay, and benchmark used it. Stored traces
   per level caught every regression.
3. **Numbers as the original.** The same float width from the start
   (C++ `float` is 32 bits, Atmos numbers are doubles): there, the
   mover went to C. Also: the real positions of objects (the converter
   rounded them), the order of objects at setup, the two phases of an
   update (move, then react), when input applies inside a tick, and
   forced against requested changes of state. Copy the clocks of the
   official code exactly.
4. **Scope decided up front.** The plan said one thing and the author
   then wanted all the official data and objects. Put the later items
   in the main milestones. A generic converter from s-expressions,
   with a list of kinds, was easy.
5. **Engine.** A single C header (about 900 lines there: image cache,
   fonts, sounds, collision maps, mover) plus thin wrappers in Atmos,
   and one C file to build (24 s at `-O2`). Hot pixel loops and exact
   float math go to C. Sprite descriptions are cached, never loaded
   per frame.
6. **Idioms that worked.** One task per entity, whose life is the
   task; a pool per draw layer (draw order is pool order); the state
   machine of an entity as a `loop` over `par :any { action } with {
   orders } with { forced }`, whose result is the next state;
   `watching` for phases that can be aborted; `toggle` for pause;
   `await Ticks(n)` for clocks; `do :tag { escape :tag }` for
   continue.
7. **Pitfalls.** `emit @:parent` from a task in a pool reaches the
   pool, not its owner: pass the receiver. A spawn inside an `if`
   block dies with the block. Iterating a tagged table gives its
   `tag`. A sprite of one frame that never ends leaks into its pool
   (it made the rain quadratic there). In `main` since then:
   `[loop=false]`, `"a\"b"`, and the error for a nested `func`.
8. **What still reads poorly there.** Objects that scan a whole pool
   every tick; the order inside a tick carried by spawn order and two
   events; records of an entity written from outside; animation clocks
   derived by arithmetic. For a game with collisions everywhere,
   decide early how they are dispatched: one broad phase in C per
   tick, which emits events to the tasks involved, rather than each
   task scanning.
9. **Environment.** The official game needed about 15 development
   packages and a few minutes to build. Its suite takes about a
   minute; comparing 159 demos, 15 to 20 minutes with 4 jobs. Heavy
   runs go to the background, and the benchmark runs alone (the noise
   is about 10% anyway). The official checkout stays outside the
   repository, and its patch inside.
10. **With the author.** Small commits, each pushed, straight to
    `main`. Design and fidelity decisions were settled alone and
    written down. What needed the author: installing packages, scope
    beyond the plan, and what to do next. Only measured numbers go
    into the documents.

## What the port may need from the compiler

Report in `doc/compiler.md`. Candidates known from Pingus:

- An await over a pool with a condition ("an entity enters my area").
- Phases inside a tick, instead of spawn order.
- 32-bit float arithmetic in Atmos.
- A shorter build for the edit and run loop.

## Risks

- **Size.** 58 thousand lines, a quarter of them menus. The first
  version leaves most menus out, so that the game screen is complete
  early.
- **The same trace.** It depends on calling the random generator in
  the same order as the original, everywhere. One call out of place
  diverges a run. The fallback is written in Fidelity.
- **Behavior in data.** Much of what the game does is in the text
  files: the port must implement the vocabulary of the engine (keys of
  enemies, powers, events), not the content.
- **Collisions and path finding.** They are the hot loops. A direct
  translation into Atmos would be slow and would bring back the
  per-frame scans: they stay in C, and emit events.
- **Many entities.** A map has dozens of enemies that think every
  frame. This is the case the runtime with trails was made for, and
  the one where a slow port would show.

## Workflow

- Commits straight to `main`, small, each with its test.
- Decisions that belong to the author are asked one at a time, with a
  recommended option.
- Installing packages needs the author's permission: ask at F0.
- Findings in the compiler are reported, not worked around in
  silence.
- Only measured numbers go into the documents.
