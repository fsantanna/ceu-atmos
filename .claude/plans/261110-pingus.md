# Plan: Pingus in Atmos

## Context

- Pingus is a free puzzle game (GPL-3) in C++, by Ingo Ruhnke and
  others.
- In 2018 its game logic was rewritten in Céu as a case study:
  "Structured Synchronous Reactive Programming for Game Development:
  On Rewriting Pingus from C++ to Céu" (SBGames 2018).
- This plan ports that rewrite to Atmos, over this compiler
  (`fsantanna/ceu-atmos`), in a later session.
- Three goals, in order:
    1. Use the control-flow patterns of the study as the design rule.
    2. Eliminate state variables: no flags, phase enums, or frame
       counters that only encode control.
    3. Replace the data format of the game (s-expressions, with their
       own reader) by data files read with `X.load`.
- The result is a third point for the study: C++, Céu, Atmos.

## Settled decisions

- **The target is the 2018 Céu rewrite**, not the 2026 sketch.
- **The patterns of the study are the design rule** (see Patterns).
- **No state variables for control** (see State variables).
- **Data files are Atmos data, read with `X.load`.** The s-expression
  reader is not ported.
- **A plan first.** This document is executed in another session.
- **The port lives in its own repository**, `atmos-lang/pingus`, with
  `ceu-atmos` as the compiler.
    - The data has 32 MB, and the game is GPL-3: neither belongs in
      the compiler repository.
    - The 2026 sketch that is there moves to a directory `old/`, or
      stays in the history: its `gui.atm` and `doc/` are reused.
    - The session that executes the plan needs both repositories.
- **The graphics layer is `lib/sdl.atm`, extended.** No `pico-sdl`.
    - It is in the compiler repository and it has a test mode with no
      screen. What is specific to the game goes in a prelude of the
      game.
- **The first version has what the Céu rewrite has**: its 17 actions
  and its 10 world objects, and the levels that only use them (see
  Scope).
- **English only** in the first version. The texts stay as keys that a
  later version can translate.
- **No demos**: no recording and no playback of `.pingus-demo`.

## Patterns

The study names five control-flow patterns. Each one has a fixed
translation in Atmos, to be applied everywhere.

| Pattern | In C++ | In Atmos |
|---------|--------|----------|
| Finite state machines | state fields and a `switch` in `update` | sequential code with `await`; the state is the position in the code |
| Continuation passing | a callback or a screen pushed for "what comes next" | `await Screen()` and what comes next is the next line; the result is the value of the task |
| Dispatching hierarchies | `draw` and `update` forwarded by hand, class by class | every task awaits `:draw` and `:clock` itself; the tree of tasks is the dispatch |
| Lifespan hierarchies | containers with explicit add and remove, and manual deletes | lexical scope, `pin`, and pools (`tasks`); the block is the lifetime |
| Signaling mechanisms | observers, flags polled every frame, global singletons | `emit` and `await` of tags, with targets (`@t`, `:parent`, `:global`) |

And three idioms that the study also discusses:

| Idiom | In Atmos |
|-------|----------|
| Wall-clock timers | `await 1s`, `watching 500ms {...}`, `loop on 40ms {...}` |
| Pausing | `toggle t(false)`, or `toggle on :Pause with :sdl.draw {...}` |
| Resource acquisition and release | `pin` of a native value, or `defer` |

Reference cases of the study, to port first and to compare line by
line:

- the Armageddon button double click (state machine);
- the Bomber action (state machine with one-shot steps);
- advancing pages in the Story screen (continuation);
- the transition from Story to Credits (continuation);
- the Bomber `draw` and `update` (dispatching);
- the game UI widgets and the Pingus container (lifespan);
- pausing the world, global keys and the options menu (signaling).

### Construct mapping, Céu to Atmos

| Céu | Atmos |
|-----|-------|
| `code/await X (...) -> T` | `task X (...) { ... }`, result as the last value |
| `await X(...)` | `await X(...)` |
| `spawn X(...) in pool` | `spawn @pool X(...)` |
| `pool[] X xs` | `pin xs = tasks()` |
| `par/or` | `par :any` |
| `par/and` | `par :all` |
| `par` | `par` |
| `watching e do ... end` | `watching e { ... }` |
| `every e do ... end` | `loop on e { ... }` |
| `await FOREVER` | `await(false)` |
| `escape v` | `return v`, or `escape :X, v` to a tagged block |
| `do ... finalize ... end` | `defer { ... }` |
| `event T e`, `emit e(v)`, `await e` | tags: `emit :e [v]`, `await :e` |
| `pause/if e do ... end` | `toggle on :e { ... }` |
| native `_f(...)`, `{ ... }` | native literals, or functions of a library |
| `var&` alias to data of another unit | a table shared by reference, or `pub` |
| `outer.x` | a captured variable, or `pub` of the enclosing task |
| static types, `data` | tagged tables |

## State variables

`cmp/state.md` classifies every field of every action. The same
classes decide what happens to each variable here.

| Class | Examples | Rule |
|-------|----------|------|
| Data only | position, velocity, direction | stays, as a field |
| Control only | `sound_played`, `gfx_exploded`, `first_bash`, phase enums | removed: the code position holds it |
| Counters for periods | `delay_count`, "every 3 frames" | removed: a loop that awaits N updates |
| Dual, sprites | current frame, `is_finished` | removed from the user: the sprite is a task that terminates, or that emits its frame |
| Action change | `set_action(x)`, `set_status(dead)` | removed: the action task returns the next action |

- The pingu is a loop over actions: each action is a task that returns
  the tag of the next one. No action enum is stored.
- A deliverable of the port is the same table again, with a third
  column for Atmos, and the count of state variables per unit.
- Review rule for every file: a `var` that is only read by an `if` or
  a `match` to decide what to do next is a state variable, and must be
  justified in a comment or removed.

## Data format

- A converter (a one-time tool, as `tst/extract.py` here) reads every
  s-expression file and writes an Atmos data file. The converted files
  are what the game loads. The s-expression reader is not ported.
- Mapping:

| S-expression | Atmos data |
|--------------|------------|
| the head symbol, `(pingus-level ...)` | a tagged table, `:pingus.level [...]` |
| `(name value)` | field `name=value` (`-` becomes `_`) |
| `(name a b c)`, scalars | field `name=[a, b, c]` |
| `(name (k v) ...)`, sublists | field `name=[k=v, ...]` |
| a list of objects, `(objects (groundpiece ...) ...)` | a vector of tagged tables, `objects=[:groundpiece [...], ...]` |
| strings, numbers | the same |
| booleans `#t` `#f` | `true` `false` |
| translatable `(_ "text")` | the string |
| enumerations as strings (`"ROT90"`, `"ground"`) | tags, `:ROT90`, `:ground` |

- A level then reads as:

```
:pingus.level [
    version = 3,
    head = [ levelname="...", number_of_pingus=20, actions=[basher=5] ],
    objects = [
        :groundpiece [ type=:ground, surface=[image="...", modifier=:ROT0], position=[10,20,0] ],
        :entrance [ ... ],
    ],
]
```

- Loading is `X.load(io.read(f, :all))`, on demand, one file at a time.
- Checks of the converter, all automatic:
    - every converted file loads with `X.load`;
    - the counts per kind match the table in this plan;
    - a second converter from the data back to s-expressions gives the
      original, up to spacing and comments (round trip).
- What is written at run time (options, progress) uses `X.dump`.
- To measure: the time of `X.load` for the largest level. If it is
  slow, the first candidate is a cache of the loaded table, not a
  binary format.

## Architecture

```
pingus/
    main.atm                the sequence of screens
    engine/                 sprite, surface, font, gui widgets
    screens/                start, menu, levels, story, worldmap,
                            options, result, credits
    game/                   game screen, playfield, input, smallmap
        objs/               world objects
        pingu/              pingu, mover, particles
            actions/        one file per action
    data/                   converted data, images, sounds
    tools/convert.py        s-expressions to Atmos data
    doc/                    the comparisons of the case study
```

- **Files are joined with `include`.** The order of the includes is
  the order of the declarations.
- **The engine is `lib/sdl.atm`, extended**:
    - mouse: `:sdl.mouse.motion`, `:sdl.mouse.dn`, `:sdl.mouse.up`;
    - surfaces: sub-rectangle, flip, rotation, alpha, scale;
    - an offscreen target, for the ground map and the small map;
    - bitmap fonts, from the `.font` descriptions;
    - music (tracker modules, through SDL_mixer);
    - the test mode with scripted mouse events.
- **The maps are C, in a prelude of the game.** The collision map and
  the ground map work per pixel, thousands of times per frame. They
  are native values with a small interface: get, put with a mask,
  remove with a mask, draw.
- **A sprite is a task.** It draws on `:draw`, advances on `:clock`,
  and terminates when a non-looping animation ends. This is what
  removes `is_finished` and frame fields from its users.
- **Draw order is spawn order**, as in the Rocks game. The rewrite
  has open issues about z-order (`ceu/TODO.md`). To decide during the
  engine milestone: keep spawn order with a fixed order of layers
  (background, objects, pingus, foreground, UI), each layer a block
  that is spawned in that order.
- **Pingus, particles, and world objects live in pools**, pinned in
  the game screen. The level ends, the block ends, everything goes.

## Scope

### First version

- Screens: start menu, levelsets and levels, story, worldmap, game,
  result, credits, and a reduced options screen.
- The 17 actions and the 10 world objects of the Céu rewrite.
- Prefabs and groups, resolved by the loader.
- The levels that only use what is implemented. The converter reports
  which ones they are. The others are not offered in the menus: unlike
  the 2018 rewrite, a missing object is not ignored silently.
- Pause, fast forward, armageddon, the small map, the action buttons.
- Sounds and music.

### Later

- The objects with no Céu version: iceblock, switchdoor, teleporter,
  generators, conveyorbelt, hammer, fake_exit, extra backgrounds.
- Translations.
- The full options screen, input configuration, controllers.

### Out

- The level editor.
- Demos (recording and playback).
- Multiplayer levels.

## Tests

- **No screen, always.** `SDL_VIDEODRIVER=dummy`, fixed frames,
  scripted input, screenshots, as the Rocks game.
- **A fixed random seed** in test mode, so that runs repeat.
- **Scripted levels.** For each tutorial level: a script of clicks,
  and the expected numbers of saved and dead pingus at the end.
- **Screenshots** at fixed frames, compared with stored ones.
- **The sanitizer** on every test run, with leak checking.
- **The data.** The converter checks, on every converted file.
- A build of the original C++ game, to compare screenshots and
  behavior, is welcome but not required: to verify if it still builds.

## What the port may need from the compiler

Known today, to confirm during the work:

- Mouse events and the other extensions of `lib/sdl.atm`.
- Speed: about a hundred tasks that await `:draw` and `:clock` per
  frame, plus the maps. To measure in P4 and P5.
- Speed of `X.load` on large levels.
- The error trace only shows call lines, not the tree of tasks. A
  game of this size may make it worth doing.
- A string with an escaped delimiter, `"a\"b"`, is a syntax error
  today. To fix before the texts of the game.
- `include` joins files in one namespace. With 80 files, name clashes
  are possible: a module as a value may become necessary.

## Risks

- **The engine is most of the unknown.** The Céu code leaned on 22k
  lines of C++. What is not game logic must come from SDL or be
  rewritten small. P1 and P4 carry this risk: do them first.
- **Draw order.** The rewrite had open z-order issues. A layer scheme
  must be fixed in P1, before the game screen.
- **Per-pixel work in Atmos would be too slow.** Keep the maps in C.
- **Levels with objects that have no Céu version.** The first version
  does not play them: say which, do not fail at run time.
- **State variables may creep back** as "just one flag". The review
  rule and the table of P8 are the guard.
- **License.** The port is a derivative work under GPL-3: keep the
  license, the authors, and the credits of the data.

## Workflow

- One commit and one push per change, in small grains.
- Run all tests before every commit, and commit only when they pass.
- Decisions that are the author's are asked one at a time, with a
  recommended option.
