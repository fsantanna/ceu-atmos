# Doom: the logic of a specialized engine, in Atmos

Plan for the repository `fsantanna/doom`, session `doom`.
Written in the `ceu-atmos` session, which maintains the compiler.

## Context

- Doom (id Software, 1993) is the opposite of the other ports. Its
  engine is highly specialized: a BSP renderer, a blockmap for
  collision, fixed-point arithmetic, a WAD format, all written for one
  game.
- The study does not rewrite that engine. It stays in C, untouched.
  Only the logic of the game is rewritten in Atmos: what decides, in
  time, what each object does.
- The question of the study: when the engine is somebody else's and
  cannot change, what is left for a language of structured reactive
  concurrency, and what does it buy?
- A second question, of its own: Doom keeps the behavior of its
  objects in a table of states. The table is an explicit state
  machine. How does it compare with tasks?
- The compiler is `fsantanna/ceu-atmos`, branch `main` (the C
  backend). Read `doc/manual.md` there before writing code.

## What the target is made of

### The table of states

`info.c` has two tables.

`states[]`, with 967 rows. A row is one frame of the animation of some
object: the sprite and frame to draw, for how many tics (1/35 s), a
function to call on entry (`action`), and the next row.

```c
{SPR_BAR1, 0,     6,  {NULL},      S_BAR2 },  // S_BAR1   idle, frame A
{SPR_BAR1, 1,     6,  {NULL},      S_BAR1 },  // S_BAR2   idle, frame B
{SPR_BEXP, 32768, 5,  {NULL},      S_BEXP2},  // S_BEXP   exploding
{SPR_BEXP, 32769, 5,  {A_Scream},  S_BEXP3},  // S_BEXP2
{SPR_BEXP, 32770, 5,  {NULL},      S_BEXP4},  // S_BEXP3
{SPR_BEXP, 32771, 10, {A_Explode}, S_BEXP5},  // S_BEXP4
{SPR_BEXP, 32772, 10, {NULL},      S_NULL },  // S_BEXP5  removed
```

`mobjinfo[]`, with 137 types of object. Each names the rows where the
type enters on each happening: `spawnstate`, `seestate`, `painstate`,
`meleestate`, `missilestate`, `deathstate`, `xdeathstate`,
`raisestate`.

| | Count |
|---|---|
| Rows | 967 |
| Rows with an `action` | 448 |
| Distinct actions | 74 |
| Types of object | 137 |
| Types with a single entry point (decoration, items) | 105 |
| Types with a `seestate` (monsters) | 20 |

What the table hides, seen in the simplest monster (the zombieman,
33 rows):

- Half of the jumps are not in the table. `A_Look` and `A_Chase` call
  `P_SetMobjState` themselves: from the table alone, one cannot tell
  that standing leads to chasing, nor chasing to attacking.
- Pain and death come from outside, into any row: the code of damage
  forces the jump.
- Animation and logic are fused: the 8 rows of chasing are one
  behavior, repeated to change the frame.

| Part | Files | Lines | How it is written |

| Menus | `m_menu` | 1893 | |

About 14 thousand lines, of 45 thousand. The rest is the engine and
stays in C: rendering, the map, movement and collision, line of
sight, sound, the WAD.

## Settled decisions

The author decided these. The items marked "(confirm)" are
recommendations that he has not answered: ask, one at a time, before
building on them.

- **Repository**: `fsantanna/doom`, commits straight to `main`, in
  small grains, pushed as you go. No other branch, no pull request.
- **The engine is not touched.** A file of logic that goes to Atmos
  leaves the build whole; it is not edited. What must change in the
  engine for the two sides to meet is the seam (see below), kept
  minimal, and listed line by line in a document.
- **The table stays only as data of animation.** The 105 types with a
  single entry point keep their rows: one generic task plays them.
  Monsters, projectiles, the barrel, and the weapons leave the table:
  their control becomes tasks. A task still fills the sprite and the
  frame of its object, which the renderer reads.
- **No saved games.** Doom saves the number of the row of each
  object, and a task suspended in an `await` cannot be saved. Save and
  load are disabled.
- **No DeHackEd**, which works by editing the table.
- **The order**: doors and lifts first, then the barrel, the
  zombieman, one weapon. How far to go after that is decided then,
  with the author.
- **Base** (confirm): Chocolate Doom at the commit above, and not
  `linuxdoom-1.10`. It builds today, runs with no screen, and exists
  to keep the demos in sync.
- **The engine in the repository** (confirm): a copy of what the
  build needs from Chocolate Doom, in one first commit with nothing
  changed. Every later change to it is then a commit of the seam, and
  `git diff` of that folder against the first commit is the whole
  seam.
- **The game data** (confirm): the shareware `DOOM1.WAD` is not
  committed (it is free to distribute, but its license is not an
  open one). A script fetches it, and the tests use its three demos.
  Freedoom is the alternative with an open license; its levels and
  demos are others.
- **Documents in English**; talk to the author in Portuguese.

## The seam

The proposal below is where the plan is least sure. The first two
milestones exist to prove it or replace it.

- **Who runs.** The Atmos program is the `main`. Its environment (a
  `:prelude`) initializes the engine, runs the main chunk, and then
  calls the frame function of the engine in a loop (`D_RunFrame`
  exists in Chocolate Doom).
- **The thinker list stays as the scheduler.** Doom runs, each tic, a
  list of "thinkers" in the order they were created; the order
  decides the sequence of the calls to the random generator, and so
  the whole game. An object whose logic is in Atmos keeps its entry
  in the list, with a thinker that only emits `:tic` to its task. So
  the order is the original one, and the port can go one type at a
  time, with the others still in C.
- **Birth and death.** The engine creates and removes objects
  (`P_SpawnMobj`, `P_RemoveMobj`, the functions that start a door).
  For a type that is in Atmos, a hook emits an event, and a task of
  the program spawns the task of the object in a pool. The removal
  ends it.
- **Jumps that come from the engine.** When code that stays in C
  calls `P_SetMobjState` on an object that is in Atmos (pain, death,
  the resurrection), the hook emits the entry point to its task
  (`:pain`, `:death`, `:xdeath`, `:raise`), which a `watching` takes.
- **Time is the tic.** `await(n, :tic)` waits `n` tics
  (`watching n, :tic {...}` and `loop on n, :tic {...}` too). It is
  in the compiler since `8ed6cbf`, made for this study.
- **The frame.** A task sets the row of its object as data (sprite,
  frame, and the pointer `state`, which two places of the engine
  compare), and never follows `nextstate` nor calls `action`. The
  duration should come from the row and not from a number in the
  Atmos code: the `-fast` mode and the Nightmare skill change the
  tics in the table when a game starts.

```
task Barrel (me) {
    watching :death {
        loop {
            await Frame(me, :S_BAR1)    ;; sets the frame, awaits its tics
            await Frame(me, :S_BAR2)
        }
    }
    await Frame(me, :S_BEXP)
    await Frame(me, :S_BEXP2) ; A_Scream(me)
    ...
}

task Zombie (me) {
    watching :death {                   ;; death interrupts all
        loop {
            await Stand(me)             ;; looks, until it sees the player
            watching :lost {            ;; lost the target: stands again
                loop {
                    watching :pain {    ;; pain interrupts chase and attack
                        loop {
                            await Chase(me)     ;; ends when it decides to fire
                            await Attack(me)
                        }
                    }
                    await Pain(me)
                }
            }
        }
    }
    await Die(me)
}
```

These are sketches, not compiled. Each `watching` is one of the jumps
that today come from outside the table, and the nesting says what
interrupts what.

## Fidelity

- **The demos are the oracle.** A demo records only the input of the
  player. The port is right when it plays the demos of the game with
  the same result, the order of the random numbers included.
- **A trace per tic**, written by a small instrumentation of the
  engine (part of the seam): the index of the random generator, and a
  checksum of the objects (position, health, row) and of the sectors
  (heights, light). The trace of the engine all in C, recorded once,
  is the expected output.
- **Every commit of a port keeps the three demos identical**, tic by
  tic. A difference is a defect of the port, never an accepted
  variation.
- **What a demo does not reach** (a monster that does not appear in
  the three demos, the intermission, a menu) needs its own input: a
  demo recorded for it, or a script of keys. Say in the study what
  was verified by demo and what was not.

## What the other ports taught

Read "What the Pingus port taught" in
`fsantanna/ceu-atmos/.claude/plans/261111-snkrx.md`. Since then:

- **A task spawned in the body of a loop, of an `if`, or of a branch
  of `match` is aborted when that block ends**, silently. It was the
  most common mistake of the ports (29 places in one of them). What
  lives longer goes to a pool of its owner (`pin fx = tasks()`), or
  is pinned outside: `pin t = if c { spawn T() }` works, since the
  task leaves the block as its value.
- **The order of awaking is in the manual**: the tasks of a block in
  the order they were attached; nested tasks and pools before the
  body of the task that holds them; a task only reacts to an emit
  that starts after its await.
- **A loop over a pool tolerates aborts and spawns in its body.**
- **A pinned value cannot be stored in a global table.** Keep one
  pinned context in the block of the pool and pass it as one
  argument.

## What the port may need from the compiler

Report to the `ceu-atmos` session, with a small program:

- An emit from C to one task (`a_emit` with a target), from inside a
  call that the program itself made into the engine.
- An event for the task that is running. A monster may damage itself
  inside its own action, and a task that is running is not awaiting.
  In C the jump takes effect at once. Find the cases, and say what
  the language should do.
- The cost of one emit per object per tic, against a call through a
  pointer.

## Risks

- **The order of the thinkers.** If tasks awake in an order that
  differs from the list, the demos lose sync at the first random
  number. The seam keeps the list for this reason; a design that
  awakes the objects by a broadcast of `:tic` would have to prove the
  same order.
- **Engine code that reads the row of an object** (`mobj->state`,
  `mobj->tics`). Few places, but each must keep seeing what it
  expects.
- **Logic and engine are not separate files everywhere.**
  `p_mobj.c` moves the objects (engine) and steps their rows (logic);
  `p_inter.c` applies damage and picks items. Where a file is both,
  the seam cuts inside it: record each cut.
- **The game data and its license.** See Settled decisions.
- **Performance.** A thinker in C is a call through a pointer. Here
  it is an emit and a resume. Measure early (D1), with many objects.
