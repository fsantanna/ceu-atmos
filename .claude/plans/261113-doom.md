# Doom: where the state machine stays, and what is left for Atmos

Plan for the repository `ia-atmos/doom`, session `doom`.
Written in the `ceu-atmos` session, which maintains the compiler.
Revised on 2026-11-13: the simulation stays in C (see "Why the
simulation stays").

## Context

- Doom (id Software, 1993) is the opposite of the other ports. Its
  engine is highly specialized: a BSP renderer, a blockmap for
  collision, fixed-point arithmetic, a WAD format, all written for one
  game.
- The study does not rewrite that engine. It stays in C, untouched.
  Only logic is rewritten in Atmos.
- The question of the study: when the engine is somebody else's and
  cannot change, what is left for a language of structured reactive
  concurrency, and where is the border?
- The answer the author reached before any code: the border is the
  saved game. What a save covers must be data, and stays as the state
  machines it is. What is around it is control, and becomes tasks.
- The compiler is `ia-atmos/lang`, branch `main` (the C
  backend). Read `doc/manual.md` there before writing code.

## Why the simulation stays

### The table of states

`info.c` has two tables.

`states[]`, with 967 rows. A row is one frame of the animation of some
object: the sprite and frame to draw, for how many tics (1/35 s), a
function to call on entry (`action`), and the next row.

```c
{SPR_BAR1, 0,     6,  {NULL},      S_BAR2 },  // S_BAR1   idle, frame A
{SPR_BAR1, 1,     6,  {NULL},      S_BAR1 },  // S_BAR2   idle, frame B
{SPR_BEXP, 32768, 5,  {NULL},      S_BEXP2},  // S_BEXP   exploding
{SPR_BEXP, 32769, 5,  {A_Scream},  S_BEXP3},  // S_BEXP2
{SPR_BEXP, 32770, 5,  {NULL},      S_BEXP4},  // S_BEXP3
{SPR_BEXP, 32771, 10, {A_Explode}, S_BEXP5},  // S_BEXP4
{SPR_BEXP, 32772, 10, {NULL},      S_NULL },  // S_BEXP5  removed
```

`mobjinfo[]`, with 137 types of object. Each names the rows where the
type enters on each happening: `spawnstate`, `seestate`, `painstate`,
`meleestate`, `missilestate`, `deathstate`, `xdeathstate`,
`raisestate`.

| | Count |
|---|---|
| Rows | 967 |
| Rows with an `action` | 448 |
| Distinct actions | 74 |
| Types of object | 137 |
| Types with a single entry point (decoration, items) | 105 |
| Types with a `seestate` (monsters) | 20 |

What the table hides, seen in the simplest monster (the zombieman,
33 rows):

- Half of the jumps are not in the table. `A_Look` and `A_Chase` call
  `P_SetMobjState` themselves: from the table alone, one cannot tell
  that standing leads to chasing, nor chasing to attacking.
- Pain and death come from outside, into any row: the code of damage
  forces the jump.
- Animation and logic are fused: the 8 rows of chasing are one
  behavior, repeated to change the frame.

### The saved game

The table has one property that tasks do not have: the position of an
object is a number, and a number can be written to a file. A task
suspended in an `await` is a point in the code, with its local
variables.

`p_saveg.c` writes everything that simulates a level:

| Saved | How |
|-------|-----|
| The objects | Each with the number of its row |
| The players | With the rows of their weapons |
| Doors, lifts, floors, ceilings, lights | The fields of each thinker: direction, counters, heights |
| The sectors and lines | Heights, textures, tags |

So to keep saved games is to keep the whole simulation as it is:
the table, and the hand-written machines of the doors as well. The
author decided to keep them.

Two ways around were considered and are not taken here: a save as a
replay of the input since the start of the level (nothing new in the
language, but the time to load grows with the time played), and a
snapshot of the tasks by the runtime (possible in this backend, where
a compiled task is a record and not a C stack; a large feature, left
as a question for the language).

## What goes to Atmos

What no save covers: the control around the simulation.

| Part | File | Lines | How it is written |
|------|------|-------|-------------------|
| The screen wipe | `f_wipe` | 302 | A melt in steps, with its own state |
| The intermission | `wi_stuff` | 1850 | Counters animated in sequence, with state variables and a pause between each |
| The finale | `f_finale` | 738 | Text typed in time, then the cast of characters |
| The flow of the game | `g_game`, `d_main` | 2861 | Two variables (`gamestate`, `gameaction`) and a dispatcher: title, demos, level, intermission, finale |
| The status bar and its face | `st_stuff` | 1471 | A face with priorities and timers |
| The messages on screen | `hu_stuff` | 759 | Messages with a timeout |
| The menus | `m_menu` | 1893 | |
| The automap | `am_map` | 1349 | Mostly drawing and input |

About 11 thousand lines, of 45 thousand.

These files draw as well: they call the primitives of the engine
(`V_DrawPatch`, the sounds, the WAD), which stay in C and are called
from Atmos.

## Settled decisions

The author decided these. The items marked "(confirm)" are
recommendations that he has not answered: ask, one at a time, before
building on them.

- **Repository**: `ia-atmos/doom`, commits straight to `main`, in
  small grains, pushed as you go. No other branch, no pull request.
- **The engine is not touched.** A file that goes to Atmos leaves the
  build whole; it is not edited. Where a file is both engine and
  control (`g_game.c` also builds the commands of the player, and
  reads and writes demos and saves), the cut goes inside it and is
  recorded. What must change in the engine for the two sides to meet
  is the seam, kept minimal, and listed line by line in a document.
- **Saved games stay, and so does all that a save covers**: the
  table of states, the objects, the weapons, and the doors, lifts,
  floors, ceilings, and lights. The simulation is not ported.
- **Save and load keep working** with the flow in Atmos. A save only
  happens inside a level, so the position of the flow at a save is
  always "in the level E, M", which the file already has.
- **A variant, for comparison only.** A second build where one door
  type (`p_doors`) and the zombieman are tasks. It has no saved
  games. It exists to put the table and tasks side by side, and to
  measure. See "The variant".
- **Base** (confirm): Chocolate Doom at the commit above, and not
  `linuxdoom-1.10`. It builds today, runs with no screen, and exists
  to keep the demos in sync.
- **The engine in the repository** (confirm): a copy of what the
  build needs from Chocolate Doom, in one first commit with nothing
  changed. Every later change to it is then a commit of the seam, and
  `git diff` of that folder against the first commit is the whole
  seam.
- **The game data** (confirm): the shareware `DOOM1.WAD` is not
  committed (it is free to distribute, but its license is not an
  open one). A script fetches it, and the tests use it. Freedoom is
  the alternative with an open license; its levels and demos are
  others.
- **How far** (confirm at each): the wipe, the intermission, the
  finale, and the flow are in. The status bar, the messages, the
  menus, and the automap are decided with the author when the first
  four are done.
- **Documents in English**; talk to the author in Portuguese.

## The seam

A proposal: the first two milestones exist to prove it or replace it.

- **Who runs.** The Atmos program is the `main`. Its environment (a
  `:prelude`) initializes the engine and runs the main chunk. The
  loop of frames is itself control: it is in Atmos, and calls the
  engine for what a frame needs (input, the tics of the simulation,
  rendering).
- **From the engine to the program.** The engine calls functions of
  the files that left (`G_ExitLevel` when the player reaches the
  exit, `WI_Start`, `F_StartFinale`, `M_StartControlPanel`). Each
  remains as a small C function, in the prelude, that emits an event
  to the program.
- **From the program to the engine.** Native calls: load a level,
  run one tic of the simulation, draw a patch, start a sound.
- **Time is the tic.** `await(n, :tic)` waits `n` tics
  (`watching n, :tic {...}` and `loop on n, :tic {...}` too). It is
  in the compiler since `8ed6cbf`, made for this study.

What the flow may look like (a sketch, not compiled):

```
task Game (skill, episode, map) {
    loop {
        await Level(skill, episode, map)        ;; until :level.exit
        await Wipe()
        await Intermission(episode, map)        ;; the counters, then a key
        if last_of_episode(map) {
            await Finale(episode)
            break
        }
        set map = next(map)
    }
}

task Main () {
    loop {
        watching :menu.newgame {                ;; a new game interrupts
            loop {                              ;; the cycle of the title
                await Page("TITLEPIC", 170)
                await Demo("demo1")
                await Page("CREDIT", 200)
                await Demo("demo2")
                ...
            }
        }
        watching :menu.endgame {
            await Game(skill, episode, map)
        }
    }
}
```

Today this is `gamestate`, `gameaction`, `demosequence`, `pagetic`,
and a `switch` on each, every tic.

## The variant

- A second build of the same repository (a flag of the build), where
  one type of door and the zombieman are tasks. Everything else is
  the main build.
- **No saved games** in it: save and load refuse.
- **The thinker list stays as the scheduler.** Doom runs, each tic, a
  list of "thinkers" in the order they were created; the order
  decides the sequence of the calls to the random generator, and so
  the whole game. An object that is a task keeps its entry in the
  list, with a thinker that only emits `:tic` to its task.
- **Birth and death.** A hook where the engine creates or removes the
  object emits an event, and a task of the program spawns the task of
  the object in a pool.
- **Jumps that come from the engine.** When code in C calls
  `P_SetMobjState` on a zombieman (pain, death, the resurrection),
  the hook emits the entry point to its task (`:pain`, `:death`,
  `:xdeath`, `:raise`), which a `watching` takes.
- **The frame.** The task sets the row of its object as data (the
  renderer reads the sprite and the frame, and two places of the
  engine compare the pointer `state`), and never follows `nextstate`
  nor calls `action`. The duration comes from the row: the `-fast`
  mode and the Nightmare skill change the tics in the table.
- **The demos are its oracle**: the three demos identical, tic by
  tic, to the main build.

```
task Door (sec) {
    await Move(sec, :up)        ;; opens
    await(150, :tic)            ;; waits
    await Move(sec, :down)      ;; closes
}

task Zombie (me) {
    watching :death {                   ;; death interrupts all
        loop {
            await Stand(me)             ;; looks, until it sees the player
            watching :lost {            ;; lost the target: stands again
                loop {
                    watching :pain {    ;; pain interrupts chase and attack
                        loop {
                            await Chase(me)     ;; ends when it decides to fire
                            await Attack(me)
                        }
                    }
                    await Pain(me)
                }
            }
        }
    }
    await Die(me)
}
```

Sketches, not compiled. Each `watching` is one of the jumps that today
come from outside the table, and the nesting says what interrupts
what.

## Fidelity

- **The screen is the oracle of the main build.** Doom draws into a
  buffer of 320x200 with 8 bits per pixel. A checksum of that buffer
  per tic, for a run with a script of input, must be identical
  between the engine all in C and the port. Screenshots of chosen
  tics are kept for the eye.
- **A test mode**, part of the seam: no window, no sound, one tic per
  frame with no real time (the wipe and the menus use real time in
  the original), and input events posted at given tics from a script.
- **The demos still play.** The simulation is not ported, but the
  flow runs them: the three demos of the game must end in the same
  state (a checksum of the objects and of the random index per tic).
- **Save and load**: a run that saves, plays on, loads, and plays the
  same input must give the same screens as the engine in C.
- **Every commit keeps all of these identical.** A difference is a
  defect of the port, never an accepted variation.
- **The variant** uses the checksum of the simulation per tic on the
  three demos, against the main build.

## What the other ports taught

Read "What the Pingus port taught" in
`ia-atmos/lang/.claude/plans/261111-snkrx.md`. Since then:

- **A task spawned in the body of a loop, of an `if`, or of a branch
  of `match` is aborted when that block ends**, silently. It was the
  most common mistake of the ports (29 places in one of them). What
  lives longer goes to a pool of its owner (`pin fx = tasks()`), or
  is pinned outside: `pin t = if c { spawn T() }` works, since the
  task leaves the block as its value.
- **The order of awaking is in the manual**: the tasks of a block in
  the order they were attached; nested tasks and pools before the
  body of the task that holds them; a task only reacts to an emit
  that starts after its await.
- **A loop over a pool tolerates aborts and spawns in its body.**
- **A pinned value cannot be stored in a global table.** Keep one
  pinned context in the block of the pool and pass it as one
  argument.

## What the port may need from the compiler

Report to the `ceu-atmos` session, with a small program:

- An emit from C into the program from inside a call that the program
  itself made into the engine (the engine calls `G_ExitLevel` while
  the task of the level is running a tic).
- In the variant: an emit from C to one task; and an event for the
  task that is running (a monster may damage itself inside its own
  action, and a task that is running is not awaiting; in C the jump
  takes effect at once).

## Risks

- **`g_game.c` is four things**: the flow, the commands of the
  player, the demos, and the saves. Only the flow leaves. The cut
  inside the file is the largest change to the engine: keep it
  mechanical (functions moved out, none rewritten).
- **Real time.** The wipe and the menus run on the clock, not on
  tics. The test mode must make them deterministic without changing
  what the player sees.
- **Engine code that reads the variables of the flow** (`gamestate`,
  `gameaction`, `paused`, `menuactive`, `demoplayback`). The renderer
  and the simulation test them. The program must keep them true, as
  data it writes.
- **In the variant, the order of the thinkers.** If tasks awake in an
  order that differs from the list, the demos lose sync at the first
  random number.
- **The game data and its license.** See Settled decisions.
